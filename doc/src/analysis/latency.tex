\subsection{First-order time model}
\label{sec:latency}

At 115\,200\,Bd with 8N1 framing a byte occupies $t_b=10/115\,200$\,s
$\approx\ByteTimeUs\,\mu$s, i.e.\ 8\,680 clocks at 100\,MHz. For a call
with $B$ wire bytes, $J$ transactions and $S$ array steps we use
\begin{equation}
  T\approx B\,t_b+J\,\tau+S\,\frac{D}{f_{\mathrm{clk}}}+T_{\mathrm{host}},
  \label{eq:time}
\end{equation}
where $\tau$ is the turnaround added per transaction beyond serialization
(USB bridge, driver and operating system; e.g.\ latency timers of USB
serial bridges~\cite{ftdi-latency}). Serialization and turnaround are
counted once each: $\tau$ excludes the bytes' own transmission time. The
model makes three simplifying assumptions: $\tau$ is the same for every
command, although buffering can make it depend on the reply size; controller
cycles outside steps are neglected, which inspection of the controller
bounds to a few clocks per word against 8\,680 per byte; and
$T_{\mathrm{host}}$, unmeasured, is omitted from comparisons.

Under these assumptions, fused execution (v3) is faster than the unfused
sequence (v2) if and only if
\begin{equation}
  \tau>\tau^{*}=t_b\,\frac{B_{\mathrm{v3}}-B_{\mathrm{v2}}}{J_{\mathrm{v2}}-J_{\mathrm{v3}}},
  \label{eq:breakeven}
\end{equation}
with $\tau^{*}<0$, i.e.\ always, when fusion also reduces bytes. A 16\,ms
turnaround, used below as one scenario, is a common latency-timer setting,
not a property measured on this platform.
